# Changelog

Cambios del SDK y notas de comportamiento del API de FiscalAPI que afectan a quien usa el SDK.

## [Sin publicar]

### Cambios incompatibles (BREAKING)

- Se elimina `Person.CapitalRegime` (estaba `[Obsolete]`): el API no tiene régimen de capital, ignoraba el valor y nunca lo devolvía. El código que lo asigna o lo lee deja de compilar: quite toda asignación o lectura de `CapitalRegime` (por ejemplo `CapitalRegime = "S.A. de C.V."` en un inicializador de `Person`) y envíe la razón social sin régimen de capital en `LegalName`.
- El API deja de devolver `stripeCustomerId` y `subscriptionStatus` en las personas (`/api/v4/people` y la persona de las reglas de descarga): eran datos internos de Stripe. Este SDK nunca los modeló en `Person`, así que el código que usa el modelo no cambia; si su integración los lee de la respuesta JSON cruda, quite esa lectura: el campo ya no llega.
- Se elimina `update` del servicio de certificados (`TaxFiles.UpdateAsync`): el API retiró `PUT /api/v4/tax-files/{id}`, que ahora responde 405 (Method Not Allowed); antes nunca actualizaba un certificado (respondía un error). Para cambiar un certificado, suba el nuevo con `TaxFiles.CreateAsync` y elimine el anterior con `TaxFiles.DeleteAsync`. El método ya no existe ni en la interfaz ni en la clase del servicio: `ITaxFileService` extiende la nueva `IImmutableFiscalApiService<TaxFile>` (consulta, creación y baja, sin `UpdateAsync`) y `TaxFileService` hereda de la nueva `BaseImmutableFiscalApiService<TaxFile>`, así que `client.TaxFiles.UpdateAsync(...)` deja de compilar (CS1061) y `TaxFileService` deja de ser un `IFiscalApiService<TaxFile>`. Los demás servicios no cambian: `IFiscalApiService<T>` extiende `IImmutableFiscalApiService<T>` con `UpdateAsync` y `BaseFiscalApiService<T>` hereda de `BaseImmutableFiscalApiService<T>`.
- Certificados: el API deja de devolver la contraseña de la llave privada (.key) en las consultas de certificados: `TaxFiles.GetListAsync`, `TaxFiles.GetByIdAsync` y la respuesta de `TaxFiles.CreateAsync` traen `password` vacía (`""`); antes, la contraseña en claro (también `GET /api/v4/tax-files/all` y `GET /api/v4/tax-files/load`, que este SDK no usa). Solo `TaxFiles.GetDefaultValuesAsync` la devuelve (a la persona misma o al owner del tenant); `TaxFiles.GetDefaultReferencesAsync` ya la devolvía vacía. El modelo `TaxFile` no cambia (su comentario XML lo documenta): la contraseña solo se envía al subir con `TaxFiles.CreateAsync`. Si su integración lee `TaxFile.Password` de una de esas consultas, use `TaxFiles.GetDefaultValuesAsync` o la contraseña que ya conoce. Ningún método ni ejemplo del SDK lee la contraseña de una consulta.

### Modelo `Person`

- Nuevos miembros (solo lectura en el API salvo `PhoneNumber`):
  - `PhoneNumber`: teléfono de la persona.
  - `Balances`: saldos por tipo de crédito (`CreditBalance`: `CreditType` y `Available`). Solo aparecen los tipos que la persona ha tenido; un tipo ausente tiene saldo 0.
  - `IsOwner`: `true` si la persona es el owner de su tenant.
  - `ValidTo` (`DateTime?`): fin de vigencia de la persona. La asigna el API; casi siempre es `null` y es informativa (no limita el timbrado ni el acceso al API).
- `Password`: requerida al crear; en `UpdateAsync`, `null` o vacía conserva la contraseña actual. El API nunca la devuelve.
- `UserTypeId`: `"C"` (cliente, el valor por omisión al crear) o `"U"` (usuario). `"T"` (tenant) solo llega en respuestas: el API lo rechaza al crear y al actualizar solo lo acepta si la persona ya es `"T"`.

### Enum `FileType`

- Nuevos valores `FileType.CertificateFiel` (`2`) y `FileType.PrivateKeyFiel` (`3`): el certificado (.cer) y la llave privada (.key) de la FIEL (e.firma), que `TaxFiles.CreateAsync` acepta y que las consultas de certificados devuelven. Antes había que convertir el número (`(FileType)2`) y un archivo FIEL llegaba en las respuestas como un valor sin nombre. Los valores existentes no cambian (`CertificateCsd` `0`, `PrivateKeyCsd` `1`) y el timbrado y la cancelación por valores siguen exigiendo en `TaxCredentials` el par del CSD. No hay valor para `4` (Pfx): el API lo rechaza (ver la nota de certificados).

### Notas del API (sin cambio de forma en el SDK)

- `Person.TaxPassword` es la contraseña de la llave privada (.key) que la persona guarda en su perfil; el API no la usa para sellar (al timbrar usa la contraseña de los certificados registrados o la de `TaxCredentials`). Solo la reciben con valor la propia persona y el owner del tenant; los demás reciben `null`. En `UpdateAsync`, `null` la conserva (el SDK omite los nulos al serializar) y `""` la borra.
- `ValidationFailure.AttemptedValue`: en un 400 de validación, el valor de un secreto (contraseñas, códigos, tokens, archivos y contraseñas de CSD/FIEL) llega enmascarado como `"[masked: n]"` (`n` es su longitud), o `"[masked]"` si la falla es de un objeto o una lista que lo contiene.
- `TaxCredential.Password` solo se exige en la llave privada (.key); en el certificado (.cer) es opcional y el API no la usa.
- `TaxFile.Tin` es opcional en `TaxFiles.CreateAsync`: si se omite (`null` o vacío), el API usa el RFC de la persona. Si se envía, debe ser el RFC de la persona (sin distinguir mayúsculas); si no, el API responde 400 con la falla en `Tin` (después de comprobar que puede gestionar los certificados de la persona; si no, 403). El API no guarda el valor enviado: el `Tin` del archivo siempre es el RFC de la persona.
- El API ya no devuelve `twoFactorEnabled` en las personas (este SDK nunca lo modeló).
- Las personas ya no traen `stripeCustomerId` ni `subscriptionStatus` (datos internos de Stripe). `ValidTo` y `CommittedBalance` son de solo lectura: el API los ignora al crear o actualizar. `CommittedBalance` es un campo heredado que el API ya no calcula y siempre vale 0; para el saldo use `AvailableBalance`, `AvailableValidationBalance` o `Balances`.
- Personas: `Persons.CreateAsync` y `Persons.UpdateAsync` con un correo que ya pertenece a otra persona, de esta o de otra cuenta (se compara sin distinguir mayúsculas ni los espacios de los extremos), responden 400 de validación con la falla en `Email` y el mensaje `The email is already registered.` (en el SDK, `Succeeded` es `false` y `Details` vale `"Email: The email is already registered."`). Antes respondía otro 400 (una falla de Identity o el genérico `A record with the same unique values already exists.`). Al actualizar, el correo actual de la persona no cuenta como repetido. El API guarda el correo sin los espacios de los extremos.
- Personas: `Persons.UpdateAsync` y `Persons.DeleteAsync` pueden responder 409 con `details` `The person was modified by another request (for example, a failed sign-in). Reload it and try again.` (en el SDK, `HttpStatusCode` 409 y ese texto en `Details`) si otra petición modificó a la persona mientras se procesaba: cuenta cualquier escritura a la persona, por ejemplo un inicio de sesión con su correo (exitoso o fallido) o un cambio en su suscripción. No se guarda nada: vuelva a consultar la persona y repita la llamada. Antes la escritura se guardaba igual y podía deshacer el cambio de la otra petición (el bloqueo de la cuenta por intentos fallidos o la sesión recién iniciada). `PATCH /api/v4/people/{id}`, que este SDK no usa, responde el mismo 409.
- Personas: `Persons.CreateAsync` y `Persons.UpdateAsync` validan el correo y la contraseña con las reglas de Identity antes de guardar. Un correo con caracteres fuera de `a-z`, `A-Z`, `0-9` y `-._@+` (por ejemplo `ñ`, una vocal acentuada, un apóstrofo o un espacio intermedio) responde 400 de validación con la falla en `Email`, `errorCode` `InvalidUserName` y el mensaje `The email contains characters that are not allowed: 'ñ'. Allowed characters: abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789-._@+` (con los caracteres rechazados entre comillas). Una contraseña que no cumple las reglas (al menos 6 caracteres, con una mayúscula `A-Z`, una minúscula `a-z`, un dígito `0-9` y un carácter que no sea letra ni dígito; las letras con acento y la `ñ` no cuentan como mayúsculas ni minúsculas) responde una sola falla en `Password` con el mensaje `Password must be at least 6 characters long and contain at least one uppercase letter (A-Z), one lowercase letter (a-z), one digit (0-9) and one character that is not a letter or a digit. Letters with accents and ñ are not uppercase or lowercase letters for this rule.`, el código del primer requisito que no se cumple en `errorCode` (p. ej. `PasswordTooShort` o `PasswordRequiresUpper`) y `attemptedValue` `null` (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo). Antes, al crear, esos valores llegaban a Identity y la falla traía el código en `propertyName` (`InvalidUserName`, `PasswordRequiresUpper`…) con el texto de Identity (p. ej. `Username '…' is invalid, can only contain letters or digits.`) (en el SDK, `Details` empezaba con `InvalidUserName:` y ahora con `Email:`); una contraseña corta como `abc` daba dos fallas (`MinimumLengthValidator` y `PredicateValidator`), y al actualizar el API guardaba un correo con `ñ` o una contraseña como `Ñandú12!` (200). Si aun así `Persons.CreateAsync` falla en otra validación de Identity, la falla trae en `propertyName` el campo del request (`Email` o `Password`) y el código de Identity en `errorCode`.
- Facturas (`Invoices.CreateAsync`): con una moneda extranjera (`CurrencyCode` distinto de `MXN` y de `XXX`), `ExchangeRate` 0 o negativo responde 400 de validación con la falla en `ExchangeRate` y el mensaje `Con una moneda distinta de MXN, 'exchangeRate' (tipo de cambio) debe ser el del día de la operación (mayor que 0).` (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo); antes pasaba la validación del API. Con `MXN` sigue siendo exactamente 1. El complemento de pagos sigue la misma regla en el tipo de cambio del pago (`Complement.Payment.ExchangeRate` frente a `Complement.Payment.CurrencyCode`): con `MXN`, exactamente 1 (el valor por omisión de `InvoicePayment.ExchangeRate`); con otra moneda, mayor que 0. Si no, responde 400 de validación con la falla en `Complement.Payment.ExchangeRate` (mensaje `Con la moneda MXN, 'exchangeRate' (tipo de cambio) debe ser 1.` o el de moneda extranjera); antes llegaba al PAC, que lo rechazaba, o el pago salía con totales en 0.
- Cambios del API en los endpoints de cuenta, que este SDK no usa (se autentica con API key), así que no le afectan: `POST /api/v4/account/register` y `POST /api/v4/account/info` con un correo que ya pertenece a otra persona responden 400 de validación con la falla en `Email` (`NewEmail` en `info`) y el mensaje `The email is already registered.`; `POST /api/v4/account/change-password` con la contraseña actual incorrecta responde 400 de validación con la falla en `CurrentPassword` (`errorCode` `PasswordMismatch`, mensaje `Incorrect password.`); en general, las fallas que vienen de Identity en `account/change-password`, `account/info`, `account/reset-password` y `account/confirm-email` traen en `propertyName` el campo del request que las causó (`CurrentPassword`, `NewPassword`, `NewEmail`, `ResetCode` o `Code`) y el código de Identity en `errorCode` (`PasswordMismatch`, `InvalidToken`, …), en lugar del código como `propertyName`; `POST /api/v4/account/refresh` con un refresh token vencido responde 401 `Invalid refresh token` en lugar de emitir otro (con uno vigente devuelve el mismo token), así que una sesión iniciada con `account/login` solo se puede renovar hasta 7 días después del login.
- Facturas (`Invoices.CreateAsync`): con `CurrencyCode` `XXX` (facturas de pago y de traslado), un `ExchangeRate` distinto de 1 y de 0 responde 400 de validación con la falla en `ExchangeRate` y el mensaje `Con la moneda XXX, 'exchangeRate' (tipo de cambio) no aplica: se omite (o se envía 1 o 0).` (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo); antes, con un valor mayor que 1 lo rechazaba el PAC (CFDI40116 en un ingreso, CRP20109 en un pago) y con uno entre 0 y 1 o negativo se timbraba ignorándolo. Con 1 (el valor por omisión de `Invoice.ExchangeRate`) o 0 se sigue timbrando, sin `TipoCambio` en el XML.
- Facturas de pago (`Invoices.CreateAsync` con `Complement.Payment`): la moneda del pago (`Complement.Payment.CurrencyCode`) y la de cada factura pagada (`CurrencyCode` de cada `PaidInvoice`) se validan contra el catálogo c_Moneda del SAT, escritas tal cual: si se omiten, no están en el catálogo (también en minúsculas, como `mxn`) o son `XXX`, responde 400 de validación con la falla en `Complement.Payment.CurrencyCode` o en `Complement.Payment.PaidInvoices[n].CurrencyCode` (`n` = posición, desde 0) con el mensaje `La moneda '<valor>' no existe en el catálogo c_Moneda del SAT.`, `La moneda de un pago o de un documento pagado no puede ser XXX.` o el de campo vacío (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo); antes llegaban al PAC, que las rechazaba (CFDI40113, CRP20213 o CRP20236). La moneda de la factura de pago (`CurrencyCode`) debe ser `XXX`: con otra, 400 de validación en `CurrencyCode` con `La moneda de un comprobante de pago debe ser XXX.` (antes, el PAC respondía CRP20104). El valor por omisión de `Invoice.CurrencyCode` es `MXN`: en una factura de pago asígnele `XXX`. Una factura sin `CurrencyCode` responde una sola falla en `CurrencyCode` (antes, dos).
- Factura global (`Invoices.CreateAsync` con `GlobalInformation.Year`): el año acepta el de la fecha de la factura (`Date`) y los 5 anteriores, como el SAT (con fecha en 2026, de 2021 a 2026); antes solo el año en curso o el anterior, y por ejemplo 2021 a 2024 respondían 400 aunque el SAT los timbra. Fuera de ese rango responde 400 de validación con la falla en `GlobalInformation.Year` y el mensaje `'year' debe ser el año de la fecha del comprobante (2026) o uno de los 5 anteriores.` (con el año de la fecha) (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo).
- Más cambios del API en los endpoints de cuenta, que este SDK no usa: `POST /api/v4/account/register` (`Email`, `Password`), `POST /api/v4/account/info` (`NewEmail`, `NewPassword`), `POST /api/v4/account/change-password` y `POST /api/v4/account/reset-password` (`NewPassword`) aplican las mismas reglas de correo y contraseña que las personas (400 con `InvalidUserName` o con la falla única de la contraseña); antes `register` creaba la cuenta con un correo con `ñ` o una contraseña como `Ñandú12!`. `reset-password` valida la contraseña nueva antes del código (con las dos inválidas, la falla es la de `NewPassword`). En `account/info`, `CurrentPassword` ya no se valida con las reglas de formato (una incorrecta responde `PasswordMismatch` en `CurrentPassword`) y es obligatoria cuando viene `NewPassword`: sin ella, 400 de validación en `CurrentPassword` con `Current password is required to set a new password.` (antes, el mismo texto en un 400 sin campo).
- Certificados: `TaxFiles.DeleteAsync` hace una baja lógica: el certificado deja de aparecer en todas las consultas y el API deja de usarlo para timbrar; borra el archivo y su contraseña y conserva solo el registro (tipo, RFC, vigencia, quién lo eliminó y cuándo). La respuesta no cambia: 200 con `true`, o 400 con `false` si no existe, ya se había eliminado o es de otra persona. Para volver a usar un certificado eliminado, súbalo de nuevo con `TaxFiles.CreateAsync`.
- Facturas (`Invoices.CreateAsync`): con el RFC genérico (`XAXX010101000` o `XEXX010101000`) el régimen fiscal del receptor debe ser `616` y su código postal el de `expeditionZipCode`; con el régimen `616` el uso CFDI debe ser `S01` o `CP01`; y una factura de ingreso (`I`) a `XAXX010101000` `PUBLICO EN GENERAL` debe traer `globalInformation`. Si no, responde 400 de validación (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo), con todas las fallas juntas, antes de timbrar y sin consumir timbre, en `Recipient.TaxRegimeCode` (`Con el RFC genérico (XAXX010101000 o XEXX010101000) el régimen fiscal del receptor (taxRegimeCode) debe ser 616 (CFDI40159).`), `Recipient.ZipCode` (`Con el RFC genérico (XAXX010101000 o XEXX010101000) el código postal del receptor (zipCode) debe ser el lugar de expedición (expeditionZipCode) (CFDI40149).`), `Recipient.CfdiUseCode` (`Con el régimen fiscal 616 del receptor, el uso de CFDI (cfdiUseCode) debe ser S01 o CP01 (c_UsoCFDI, CFDI40161).`) o `GlobalInformation` (`Un ingreso a XAXX010101000 'PUBLICO EN GENERAL' es una factura global: globalInformation es obligatorio (CFDI40130).`). Vale igual con el receptor por valores y por referencia (`Recipient.Id`: se revisan los datos de la persona guardada). Antes las rechazaba el PAC con un 400 sin campo (CFDI40159, CFDI40149, CFDI40161 y CFDI40130).
- Facturas: la factura que devuelven `Invoices.CreateAsync` y `Invoices.GetByIdAsync` trae `Invoice.GlobalInformation`: completa (`PeriodicityCode`, `MonthCode` y `Year`) en una factura global, o `null` si no es global o si es una global timbrada antes de este cambio (el XML timbrado conserva la información global). Antes la respuesta no traía el campo (el modelo quedaba en `null`).
- Facturas (`Invoices.CreateAsync`): el tipo de factura y sus complementos deben corresponder, como exige el SAT: `I` admite `complement.localTaxes`, `complement.cartaPorte` y `complement.comercioExterior` (o ninguno); `E`, `complement.localTaxes` y `complement.comercioExterior` (o ninguno); `T` requiere `complement.cartaPorte` o `complement.comercioExterior`; `P` requiere `complement.payment` y `N`, `complement.payroll`; `T`, `P` y `N` no admiten otro complemento. Si falta el complemento que el tipo requiere, viene uno que no le corresponde (por ejemplo `payroll` en un ingreso, `cartaPorte` en un pago o `localTaxes` en un traslado) o `complement` llega vacío, responde 400 de validación con la falla en `Complement` (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo), antes de timbrar y con el mensaje del tipo: `Un comprobante de tipo I (ingreso) no lleva complement o solo lleva complement.localTaxes, complement.cartaPorte o complement.comercioExterior.`, `Un comprobante de tipo E (egreso) no lleva complement o solo lleva complement.localTaxes o complement.comercioExterior.`, `Un comprobante de tipo T (traslado) requiere complement.cartaPorte o complement.comercioExterior y no admite otro complemento.`, `Un comprobante de tipo P (pago) requiere complement.payment y no admite otro complemento.` o `Un comprobante de tipo N (nómina) requiere complement.payroll y no admite otro complemento.` Antes, sin el complemento que el tipo requiere (o con `complement` vacío) respondía un error 500 (`No mapper found for invoice request`); con un complemento que no le correspondía, la factura llegaba al PAC, que la rechazaba (por ejemplo CRP20101 con `payment` fuera de `P` o CP114 con `cartaPorte` en `P` o `E`), o el complemento sobrante se omitía sin aviso (por ejemplo `localTaxes` en un pago), y un `I` con `payroll` se enviaba como nómina (`N`). `POST /api/v4/invoices/calculate`, que este SDK no usa, responde igual, y con un `typeCode` fuera del catálogo responde 400 en `TypeCode` (antes, 500).
- Facturas (`Invoices.CreateAsync`): el 400 de un `typeCode` fuera del catálogo dice `El tipo de comprobante '<valor>' no existe en el catálogo c_TipoDeComprobante del SAT.` (antes `Please use the SAT catalog values: I,E,T,P,N,P`, con la `P` repetida; ver la nota de claves de catálogo del timbrado).
- Facturas (`Invoices.CreateAsync`): una fecha ausente, `null`, vacía o que no se reconoce como fecha responde 400 de validación en el campo (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo) en lugar de llegar al PAC como `0001-01-01` (que la rechazaba con CFDI40101 o CFDI40999): `date` → `Date` con `'date' es obligatorio y debe ser una fecha con el formato yyyy-MM-ddTHH:mm:ss.`; `complement.payment.paymentDate` → `Complement.Payment.PaymentDate` con `'paymentDate' es obligatorio y debe ser una fecha con el formato yyyy-MM-ddTHH:mm:ss.`; y `complement.payroll.paymentDate`, `initialPaymentDate` y `finalPaymentDate` → `Complement.Payroll.PaymentDate`, `Complement.Payroll.InitialPaymentDate` y `Complement.Payroll.FinalPaymentDate` con `'<campo>' es obligatorio y debe ser una fecha con el formato yyyy-MM-dd.` (`'paymentDate'`, `'initialPaymentDate'` o `'finalPaymentDate'`). En este SDK, `Invoice.Date`, `InvoicePayment.PaymentDate`, las tres fechas de `Payroll` y `Ubicacion.FechaHoraSalidaLlegada` de Carta Porte son `DateTime` (no anulables) y siempre se envían: si no se asignan viajan como `0001-01-01T00:00:00`, que el API trata como fecha ausente (una fecha del año 1 cuenta como ausente) y responde ese 400 en el campo sin ir al PAC. Antes, con la zona horaria de México (`TimeZone` por omisión `America/Mexico_City`), el API convertía ese valor a otra hora del año 1, no lo reconocía como ausente y la factura llegaba al PAC, que la rechazaba (CFDI40101 o CFDI40999).
- Facturas (`Invoices.CreateAsync`): una factura `I`, `E` o `T` sin `items` (o con la lista vacía) responde 400 de validación con la falla en `Items` y el mensaje `items debe tener al menos un concepto en los comprobantes de tipo I, E y T.` (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo), sin ir al PAC; antes la rechazaba el PAC (CFDI40999 o CP999: el nodo `Conceptos` es obligatorio en el CFDI). En `P` y `N` se siguen omitiendo: el API genera el concepto. `POST /api/v4/invoices/calculate`, que este SDK no usa, aplica la misma regla (antes respondía 400 sin mensaje) y, con un total 0 (todo `T` y `P`, o un ingreso con descuento del 100 %), responde 200 con el cálculo (antes, 400 con `succeeded` `false`).
- Facturas con Carta Porte o Comercio Exterior (`Invoices.CreateAsync`): el API valida los datos de esos complementos antes de timbrar (obligatorios, longitudes, patrones y catálogos del SAT): una falla responde 400 de validación con la falla en el campo, en `Complement.CartaPorte.…` o `Complement.ComercioExterior.…` (por ejemplo `Complement.CartaPorte.Ubicaciones[0].NumEstacionId` con `NumEstacionId must be a valid c_Estaciones value.`) (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo), sin consumir timbre; antes esas reglas no se aplicaban y el PAC rechazaba la factura (CPxxx, CCExxx o CFDI40101). La fecha de salida o llegada de cada ubicación de Carta Porte sigue la regla de las demás fechas: ausente, vacía, del año 1 o ilegible responde 400 en `Complement.CartaPorte.Ubicaciones[n].FechaHoraSalidaLlegada` con `'fechaHoraSalidaLlegada' es obligatorio y debe ser una fecha con el formato yyyy-MM-ddTHH:mm:ss.` (antes llegaba al PAC como `0001-01-01`). Las claves de estación (c_Estaciones) se escriben como en el catálogo del SAT, con acento cuando lo llevan: `Juárez0` se acepta y `Juarez0` responde 400. El `NumRegIdTrib` del receptor del complemento Comercio Exterior (`ComercioExterior.Receptor.NumRegIdTrib`) se ignora, como antes: el API usa el del receptor del CFDI (`InvoiceRecipient.ForeignTin`, o el de la persona receptora por referencias); puede omitirlo.
- Facturas: los errores de lectura del request (un valor de otro tipo, JSON mal formado, cuerpo vacío o un campo obligatorio ausente o `null` dentro de un complemento, por ejemplo `Complement.CartaPorte.TranspInternacId` con `'transpInternacId' no debe estar vacío.`) responden el mismo 400 de validación que las demás reglas, con la falla en el campo, en lugar de un ProblemDetails (`application/problem+json`): en el SDK, antes `Message` y `Details` llegaban en `null` (el SDK no lee ProblemDetails); ahora `Succeeded` es `false`, `Message` es `Sorry, it's not me, it's you.` y `Details` trae las fallas como `Campo: mensaje` separadas por `; `. En esas fallas `errorCode` es `null`. Un cuerpo que no se puede leer responde una sola falla: un valor de otro tipo, en su ruta (por ejemplo `$.items[0].quantity`), y un JSON mal formado, en `$` (la raíz del JSON), ambos con el texto en inglés del lector de JSON; un cuerpo vacío o `null`, en `$` con `El cuerpo de la petición es requerido y no debe estar vacío.` El ProblemDetails de antes traía además en `errors` la clave del parámetro del endpoint (`command`, `The command field is required.`) y, con un cuerpo vacío, la clave vacía (`""`); ya no llegan. Vale para todos los endpoints.

- Cancelación (`Invoices.CancelAsync`, por valores y por referencias): `cancellationReasonCode` debe ser una clave del catálogo c_MotivoCancelacion del SAT (`01`, `02`, `03` o `04`); otro valor responde 400 de validación con la falla en `CancellationReasonCode` y el mensaje `El motivo de cancelación '<valor>' no existe en el catálogo c_MotivoCancelacion del SAT.` (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo), sin llamar al PAC. Antes solo se exigía que no estuviera vacío y cualquier otro valor llegaba al PAC (el de pruebas llegó a cancelar con un motivo inexistente; el SAT lo rechaza con el código 311). Un motivo vacío sigue respondiendo el mensaje de campo vacío, y `01` sin `replacementUuid`, la falla en `ReplacementUuid`, como antes.
- Certificados (`TaxFiles.CreateAsync`): `fileType` `4` (Pfx), que el API aceptaba sin documentarlo y que ningún flujo usa, responde 400 de validación con la falla en `FileType` y el mensaje `'File Type' 4 (Pfx) no se admite: el certificado (.cer) y la llave privada (.key) se cargan por separado (fileType 0 y 1 para el CSD, 2 y 3 para la FIEL).` (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo); antes respondía 200 y guardaba el archivo. Los tipos admitidos son `0` y `1` (certificado y llave privada del CSD) y `2` y `3` (certificado y llave privada de la FIEL); otro valor sigue respondiendo `'File Type' tiene un rango de valores que no incluye '<valor>'.`
- Elementos `null` en listas (facturas `Invoices.CreateAsync`, también `POST /api/v4/invoices/calculate`, que este SDK no usa; productos `Products.CreateAsync` y `Products.UpdateAsync`; cancelación `Invoices.CancelAsync`, por valores y por referencias): cada elemento de una lista de objetos del cuerpo debe ser un objeto. Un elemento `null` (por ejemplo, en `items`, `relatedInvoices`, las percepciones de nómina, `productTaxes` o `taxCredentials`) responde 400 de validación con `Sorry, it's not me, it's you.` y `One or more validation failures have occurred.`, una falla por cada elemento `null` (en el SDK, `Succeeded` es `false` y `Details` trae las fallas con su campo), antes de las demás validaciones y sin llamar al PAC ni consumir timbre. `propertyName` es la ruta del elemento con su posición (por ejemplo, `RelatedInvoices[0]`, `Items[1]`, `Complement.Payroll.Earnings.Earnings[0]`, `ProductTaxes[1]` o `TaxCredentials[0]`) y el mensaje es `'<campo>' no admite elementos null: cada elemento debe ser un objeto.`, con el campo como en la API en las facturas (`'relatedInvoices' no admite elementos null: cada elemento debe ser un objeto.`) y separado en palabras en productos y cancelación (`'Product Taxes'`, `'Tax Credentials'`). Antes, la mayoría de estos casos respondía 500 (`Something went wrong on our end.`) y algunos se aceptaban ignorando el elemento (en las facturas, `propertyInfo`, `parts` y `customsInfo` de los conceptos se timbraban sin él; en la cancelación por referencias, `taxCredentials` se ignoraba); `taxCredentials`, `paidInvoices`, `paidInvoiceTaxes` y `ubicaciones`, que ya respondían 400 con otro texto (la falla del par de certificados y `no debe estar vacío.`, `no debe estar vacío.` o el mínimo de 2 ubicaciones), responden ahora solo esta falla. Las listas de textos conservan su regla y `metadata` (un diccionario) sigue aceptando valores `null`. El SDK no agrega elementos `null` por su cuenta: solo se envían si su código los pone en una lista (por ejemplo, `new List<InvoiceItem> { item, null }`).
- Certificados y llaves privadas: una contraseña que no abre la llave privada (.key) responde 400 de validación con la falla en el campo de la contraseña y el mensaje `La contraseña de la llave privada (.key) es incorrecta o el archivo no es una llave privada.` (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo), antes de llamar al PAC y sin consumir timbre: en `Invoices.CreateAsync` con el emisor por valores (`taxCredentials` del emisor), en `Issuer.TaxCredentials[n].Password` (`n` = posición de la llave, desde 0); en `TaxFiles.CreateAsync` con una llave privada (`fileType` `1` o `3`) y en `Manifests.SignAsync`, en `Password`. El mismo mensaje sale si el archivo enviado como llave no es una llave privada. Antes respondía 400 sin falla de validación, con `The .KEY's password is incorrect.` La cancelación por valores (`Invoices.CancelAsync`) no abre la llave: la revisa el PAC, como antes. Un certificado o una llave recibidos que no se pueden leer, en un flujo sin esa revisión (por ejemplo, un .cer ilegible en `Manifests.SignAsync`), responden 400 con `No se pudo leer el certificado (.cer) o la llave privada (.key).` (en el SDK, `HttpStatusCode` 400 y ese texto en `Details`) (antes, `The .KEY's password is incorrect.`). Si el API no puede descifrar un dato protegido que guarda (por ejemplo, la contraseña de los certificados de una persona al timbrar o cancelar por referencias, o en `TaxFiles.GetDefaultValuesAsync`), responde 500 con `Sorry, it's not you, it's me.` y `No pudimos descifrar un dato protegido del servidor. Escríbenos a soporte@fiscalapi.com.` (en el SDK, `HttpStatusCode` 500 y ese texto en `Details`): es un error del servidor, no de la petición; escriba a soporte. Antes respondía 400 con `The .KEY's password is incorrect.`
- Datos de empleador y de empleado: `Persons.Employer.CreateAsync` para una persona que ya tiene datos de empleador responde 400 de validación con la falla en `PersonId` y el mensaje `La persona ya tiene datos de empleador: modifícalos con PUT /api/v4/people/{personId}/employer.`, y `Persons.Employee.CreateAsync` para una persona que ya tiene datos de empleado, con la falla en `EmployeePersonId` y el mensaje `La persona ya tiene datos de empleado: modifícalos con PUT /api/v4/people/{personId}/employee.` (en el SDK, `Succeeded` es `false` y `Details` trae la falla con el campo); modifíquelos con `Persons.Employer.UpdateAsync` o `Persons.Employee.UpdateAsync`. Antes respondía 400 sin falla de validación, con `Sorry, it's not you, it's me.` y `A record with the same unique values already exists.`
